## 1. 生效范围与优先级

用户的现行明确指令优先。本文件是后续协作权限、审核和交接的唯一公共规则；
当前 Order 决定具体目标、产品/方法契约、可写模块、资源预算和必要验证。
V3 取代旧规则中的逐文件授权默认、固定提交数、仅非语义自修、失败次数停机、
每次局部修复重签 Order、日常工作一律提前认证以及一律全量重跑。
未来 Order 若收紧某项自主权，必须写明具体风险、对应条款及适用范围；
复制旧模板中的限制或笼统“严格遵守”不构成有效收紧理由。
Order 不得扩大用户保留授权的边界。

V2 协议、已签发 Order、旧入口和历史记录原文保留。它们描述历史操作与工具的
具体技术契约，不是重新启用旧协作限制的依据。已冻结运行始终按当时输入解释。
V3 不改变现有 runner/schema/CLI，不向旧 manifest 塞入新字段，也不使未认证工具
自动成为 CERTIFIED。新工作如需不同工具能力，按第 7 节完成相应实现与审核。

在 EXECUTING 中不修改正在执行的 Order、输入或预算。澄清使用独立补充记录，
改变契约或冻结输入前先在安全边界暂停相关动作并交接；无关的已授权工作可继续。
当前 EVAL-002 的接入由 ACTIVE_WORKFLOW.json 中的显式补充规则限定。

## 2. 角色和保护边界

Commander 是目标/契约制定者和唯一最终审批者，维护 Order、review、decision、
Commander state；不代写功能实现。Builder 是唯一功能实现写入者，维护自己的
计划、代码、测试、结果、报告和 Executor state；不自我审批，不自改验收标准。
两个角色可并行阅读；同一功能工作区保持单写者。流程维护会话不自动获得任一角色。

正式源 checkout `/home/mint/rl_dev/instinctRL`、冻结 runtime
`/home/mint/rl_blackwell_test` 和历史证据保持只读。产品工作区是
`/home/mint/rl_dev/worktrees/instinctRL-blackwell`，产品分支 `blackwell-migration`；
coordination 是独立仓库。legacy runtime 不因流程升级而成为可写模块。

actor 只接收已批准的传感器/测量历史、有效性/时间、IMU 派生字段和指令信息。
位姿、里程计、实际/显式估计速度、地图、SLAM、障碍物真值和 simulator 私有状态
不能进入 actor。已批准的 reward/critic/evaluation/logging 特权使用及底层飞控
稳定控制保持原边界；以当前产品契约为准，不在流程文档中发明新输入。

改变研究方法、actor 契约、冻结 runtime、系统/驱动/包、正式训练或新增训练额度、
merge/push、破坏性操作仍须相应用户授权。已有明确授权持续有效，不重复索要。
Commander 可在已有用户授权内安排工作，但不能自行增加这些权限。

## 3. Builder 的任务内自主权

授权边界是“使实现符合既定契约”，不以“代码是否改变语义”为界。
在当前可写模块内，Builder 可直接修复产品 bug、测试、解析器、比较器、调用接线、
路径/schema 适配、文档和证据封装，也可增加 helper、调整内部函数与文件拆分。
仅进行达到任务目标所需的局部重构。固定产品的诊断 Order 仍禁止修改产品文件。

修改校验器以正确实现既定标准属于实现修复；改变标准、阈值、指标定义、比较域、
物理/actor/方法契约属于契约变更，必须提交 Commander 判断，不能以修复名义绕过。
普通 workload/分析代码与公共核心工具分别按第 7 节处理。

默认授权模块目录及对应测试目录，而非穷举每个 helper。受保护路径优先；解析
实际路径，禁止借 symlink、路径穿越、目录移动或导入副作用越界。跨模块修改需
Commander 补充范围，但本来已在模块范围内的新文件不需要逐个审批。
只读检查、廉价本地测试和范围内诊断默认可用；仿真、GPU、训练等遵守实际预算。

Builder 自选合理原子提交，无 nominal/repair 提交数量上限，不因提交数量失败。
默认 additive commits；不改写已审提交、冻结输入和历史证据。amend/rebase 或其他
history rewrite 仍须明确授权。无需为了满足模板拆出无意义的文档提交。

计划默认 INLINE，无中间审批。局部失败留在 EXECUTING，同一 Order 内修复并重跑
受影响检查。三次无新证据的尝试触发诊断总结和方法调整，不自动 BLOCKED；
禁止重复盲跑。实际运行预算仍是硬上限，不因换 attempt 或修复次数重置。

## 4. Order 和执行前检查

使用 [V3 Order 模板](../templates/ORDER_V3.md)，写清以下信息即可：目标/完成标准、
基线、可写模块/保护路径、冻结契约、运行预算、必要检查及证据等级。
实现步骤和 helper 命名交给 Builder。以可观察行为验收，避免锁死未经验证的实现假设。

Commander 签发前检查目标是否能在指定模块、冻结输入、工具接口和预算内完成；
例如新 attempt ID 是否可传入、所选 mesh 是否真的被传感器读取。
不要求为此新建认证项目，源检查和已有廉价测试足够时直接使用。

Builder 开始和恢复时核对 current Order、两方状态、实际 HEAD/分支、相关 diff、
保护输入及剩余额度。初次基线应匹配；续作核对已记录的 additive 后继关系，
不能因自己已经提交就认为 BASE_COMMIT 漂移。无关脏文件保留且不暂存；
受保护输入有未知变更时暂停依赖它的动作。STOP 文件出现时停止新的任务动作，
仅做安全停止、必要清理和证据保全，不继续实验。

## 5. 审核分级与复审

每条 finding 至少说明：类别、证据、违反的契约、受影响结论和关闭条件。

| 类别 | 判据 | 处理 |
| --- | --- | --- |
| MUST_FIX | 实现不满足目标、actor 泄漏、结果不可信、必要证据/测试缺失 | REWORK_REQUIRED；Builder 在原 Order 内修复 |
| NON_BLOCKING | 不影响正确性、可追溯性或所声称结论的文案/命名/展示问题 | APPROVE，记录观察；无需新修复循环 |
| FOLLOW_UP | 新功能、可选优化、额外覆盖、未约定的改进 | 进入后续任务，不追加入当前验收 |
| CONTRACT_DECISION | 契约冲突、超范围依赖、确需新增权限 | Commander 解决或补充 Order；确需用户权限才 HOLD |

必须具备的原始证据不能以“非阻塞”豁免；测试全绿也不能掩盖真实缺陷。
Commander 一次汇总已发现的实质问题；复审检查修复、影响面和此前未完成的必要项。
新发现的重大缺陷仍可阻塞，但须给出具体证据；不得靠不断添加风格偏好或新需求延长验收。
已满足 gates 且只有 NON_BLOCKING/FOLLOW_UP 时直接 APPROVE，可在评语中附观察，
不新增必须由工具识别的审批枚举。

校验器误报、证据缺陷与产品缺陷分别记录；“产品尚未被证明”不等于“产品错误”。
前两者不撤销未变化产品的既有正确结论，但相关未证实结论不得宣称通过。
性能只有被当前 Order 明确指定为验收阈值时才阻塞；诊断中的差表现应如实报告。

## 6. 状态、交接与预算

保留现有状态枚举以兼容 V2：Builder 使用 IDLE / PLANNING /
PLAN_READY_FOR_REVIEW / EXECUTING / READY_FOR_REVIEW / BLOCKED；Commander 使用
IDLE / ORDERED / REVIEWING / APPROVED / REWORK_REQUIRED / HOLD。
仅当 Order 有具体理由要求计划审批时才停在 PLAN_READY_FOR_REVIEW。

正常循环：Order → Builder 自主闭环 → READY_FOR_REVIEW → Commander 汇总审核 →
APPROVED 或原 Order 局部修复 → 针对性复审。审批后由 Commander 下达下一任务，
Builder 不自行扩大目标；现有本地状态/报告用于交接，不要求用户逐项转述。
没有自动调度器时在交接点结束本轮，由用户或已有客户端唤起另一会话；
不得声称已自动唤醒另一个 agent。

BLOCKED 只用于确实无法继续的权限、输入、资源或预算缺口，报告具体缺口、
已完成部分和所需动作。普通失败、修复次数、文件命名不构成 BLOCKED。
某一动作受阻时继续独立的已授权工作，不盲目消耗运行额度。
失败启动、初始化、重试均按 Order 计账；不同目录/分析版本共享同一运行预算。
有效结果完成后停止，不为消耗余额补跑；不得筛选有利样本或隐瞒失败。

## 7. 开发、正式证据与工具分层

| 证据等级 | 用途 | 默认要求 |
| --- | --- | --- |
| STANDARD | 日常实现、集成与行为诊断 | 候选版本、diff、必要测试/关键日志/结果；Builder 自测冻结，交付时统一审核 |
| FORMAL | 正式 benchmark、发布验收、可复现性正式声明 | 事前固定方法、数据/种子选择、关键工具和输入；完整运行证据及独立审核 |

STANDARD 不要求为所有探索命令建立认证账本，也不强制多份内容重复的 devlog。
影响验收的测试及所有消耗预算的运行仍须保存真实 argv、相关环境、退出码、
stdout/stderr、输入身份和结果。探索失败若影响最终结论必须披露。
不得记录无关秘密或整个敏感环境；只记录可复现所需的非秘密配置。
FORMAL 沿用适用的 certified runner/sealer 技术契约及全部必要证据。

公共核心工具（启动隔离、预算/身份检查、原始记录、封存）仍固定精确版本。
改动它们的执行/完整性语义必须在使用新版本做正式声明前由 Commander 审核；
在明确授权工具模块内可自主开发、自测，不需要每个修复单独申请。
普通 workload、离线解析器、指标回放和分析测试在授权模块内可随交付审核，
无需逐提交中间认证。正式结论仍必须完成该分析版本及验收标准的独立审查。
优先复用现有工具，不为每个任务创建私有 runner/sealer。

## 8. 冻结运行、独立分析与证据复用

运行记录与分析记录分别编号。运行记录固定产品/运行工具/输入/原始输出；
分析记录固定读取的运行文件及哈希、分析器版本、标准版本、命令和结果。
可用 `<ORDER_ID>-A0001` 命名离线分析记录，默认存放
`analyses/<ORDER_ID>/<ANALYSIS_ID>/`；这是独立记录，不能伪装为旧 runner 的 attempt。
一份 Markdown 或 JSON 可记录上述字段，无需新增强制 schema/认证工具。

原始运行开始后冻结输入；生成完毕的原始结果不覆盖。已 SEALED 或已终止/拒绝且
要求保留的 attempt 全部只读。修复解析器后创建新分析版本，指向原始文件，保留
旧分析和差异解释。DRAFT 的索引/展示/非语义封装可在披露后局部修复，不能借
DRAFT 身份改写已执行源、输入、原始观测或失败事实。

当旧证据固定了工作区内的源码绝对路径，保留该路径的 bytes；需要修复的版本可在
`/home/mint/rl_dev/worktrees/` 下创建有记录的隔离 Git worktree/checkout。
此可逆操作属于任务内自主权，须记录来源仓库、base、实际分支/路径和新候选版本；
相同仓库相对模块的授权映射过去，保护路径、单写者和总预算不变。隔离分支可以
使用任务专属名称，不能据此更改主工作区的固定 HEAD 或 merge/push。不得把源码
放进旧 attempt，也不能仅保留 Git 历史就声称原绝对路径哈希仍然匹配。

复用必须证明：原始输入和文件身份可信，数据完整，覆盖待证明的契约，修改仅影响
后处理，未更改所需运行行为。满足时只跑受影响的离线检查，不重新启动仿真。
原始数据缺失/损坏、必要观测未采集、运行行为需改变或可复现性本就要求新运行时，
才在剩余授权预算内重跑相关部分；不能复用旧数据声称新产品行为已验证。

验收比较域预先区分科学结果、资源阈值、运行元数据。JSON 对象按键集/值比较；
列表顺序、浮点容差按契约；PID/时间/路径/空闲显存不默认跨运行精确相等。
其身份、格式及资源安全仍须独立验证。事后改变标准必须由 Commander 记录理由、
旧/新判定及全部受影响样本；不能为了 PASS 静默删字段或放宽阈值。涉及研究方法
时沿用用户授权边界。

V3 的分析记录不替代当前 Order 明确要求的 certified seal。旧工具不支持某种新
封装时，保留旧包，输出独立分析供审核；需要正式新封装才安排有界工具适配。
不得仅因旧工具没有新字段就重跑有效仿真，亦不得伪称工具已提供新能力。

## 9. 最小交付与流程改进

一份报告链接：目标完成情况、候选 commit/diff、必要测试/结果、输入与原始证据、
累计运行预算、关键实现决策、修复影响、未解决事项和限制。只重跑受影响检查；
扩大回归须有新的变更、失败或依赖风险依据。缺失的必要验证明确 NOT PROVEN。

接下来三项新任务，在最终报告中顺带记录交接次数、用户决策次数、仅因证据问题
重跑的仿真次数、MUST_FIX 的原因及审核后发现的实质遗漏；不另建审核项目。
用这些记录调整流程，不能把“零返工”作为压制真实缺陷的目标。
