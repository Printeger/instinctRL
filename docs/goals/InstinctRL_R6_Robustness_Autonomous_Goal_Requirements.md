## 7. 训练期间不常驻 Codex：必须实现并验收

项目 Goal 是持久化任务，不等于一个必须持续在线的聊天会话。采用现有普通 Python 控制器的增量改造，放在 tmux 或已有服务管理方式下；不新建通用平台、不安装调度依赖。仅挂起聊天中的工具调用或让模型反复 sleep，不算完成此要求。

推荐状态流：

```text
CPU_PREPARE → PRELIVE_REVIEW → WAIT_RESOURCE → RUNNING_JOB
→ CLOSE_AND_SETTLE → CPU_ANALYZE
→ {EXECUTE_REGISTERED_NEXT, MODEL_DECISION, FINAL_REVIEW}
MODEL_DECISION → {REPAIR_AND_REVIEW, NEW_CANDIDATE, FINALIZE}
```

- 控制器是唯一 submit/cancel/settle/终态写入者。模型可在交接窗口修改任务代码和拟定新计划，不直接发车、不另开控制器。控制器持有总锁，并在模型写入期间不写开发树；独立reviewer只读。
- 训练等待时，控制器以15–60秒本地轮询精确job或等待进程事件；不调用任何模型。CPU解析、哈希、表格和预登记条件分支由脚本完成，不“每次checkpoint唤醒Codex”。
- 模型只在新方法/精确计划审核、无法按既定规则解释的故障、需要科学决策的批次总结、最终独审时启动。能合并审核一个批次时合并；不能将实现者自评冒充独审。
- 每次模型输入只传当前状态、预算差额、机器生成的分项摘要、必要失败片段和证据索引，默认prompt及摘要合计≤64KiB；不用继承整个历史聊天，不把全量raw或数千行训练日志倒进上下文。模型按需读取准确原件，不能以摘要代替必要的独立证据核查。将上下文瘦身与完整原件保全分开。
- 一次模型会话只完成一个具体决策/修复包，写结构化产物、保存receipt后退出。其下一段训练由控制器接续；该模型不在后台等待训练。
- 幂等键至少包含goal_id、event_id、job_id、输入哈希、角色。启动前原子保存intent，结束保存准确进程身份、退出码、产物hash和usage。已消费事件不重复唤醒。缺receipt不表示未执行，先查真实job/进程/文件，不能重提或重跑副作用。
- 先提交模型prompt/schema、工具与CLI身份；stdin传文本、JSONL收事件、独立保存最终JSON和stderr。输出字段包括decision、证据pins、变更文件、next_plan、remaining_budget和must_fix；代码独立验证，不按模型一句“PASS”直接发车。
- 明确的纯网络/服务临时失败，可由本地控制器有限退避后重试未完成的模型事件，但须确认无在途worker/未核对副作用，所有会话占用32次总额；认证失败不得自动换账户/付费渠道。问题未恢复时本地保存待办，不周期性唤醒另一模型询问状态。
- worker与controller分别记录身份，异常恢复只重接准确在途作业。PID之外记录启动时间/boot身份等，防PID复用；重复controller由锁拒绝。receipt、清理、postrun和预算结算均幂等。

**启动会话的交接要求：**部署后用有界检查证明控制器已脱离终端运行、锁/状态/日志/唤醒机制有效，随后主动结束启动会话。明确写“后台运行中，未完成”，不能把成功启动说成科学完成，也不能保持Goal UI自动推理轮询。平台若没有无需模型推理的事件等待/恢复能力，使用本地controller作为任务真状态，并以结束当前轮次完成交接；不得伪造“暂停/完成”状态来省token。需要平台级权限才能禁用自动续推理时，必须在发车前说明该具体限制，不能承诺已实现零模型等待。

**正式长训前的自动化验收：**用CPU替身完成job结束→事件去重→结构化决策→下一步骤的恢复测试；模拟controller重启、模型worker死亡、半写receipt、STOP、重复提交意图。随后最多一次有记录的真实非交互审核调用，证明已安装CLI/认证/结果schema可用，该调用计入总额并承担真实审核任务，不做额外付费空探测。

后台连续运行的一段训练等待窗口内，进程/事件日志应证明仅controller与训练进程活跃，没有本任务Codex worker、没有新增模型调用。最终 `MODEL_USAGE_AUDIT.json` 报告训练等待时长、模型调用数/原因/usage/重复事件拒绝数；要求自动纯等待调用为0。不保证后台训练或API本身免费。

本机文档编写时CLI为0.161.0，help支持 `exec`、stdin、`--json`、`--output-schema`、`--output-last-message`。启动时重新核对本机帮助，不能把旧runner固定版本或旧完整命令当兼容证明。平台权限必须使用当前支持的配置，不绕过外部审批或信任边界。非交互接口依据[OpenAI官方说明](https://developers.openai.com/codex/noninteractive)；事件调度、去重、预算及等待退出是本项目必须实现的逻辑，不是CLI自带的训练编排保证。

## 8. 资源准入与故障恢复：吸取已发生的教训

- 不复用“所有瞬时采样≤5%”作为永久阻断。新任务可先复用已记录的V2窗口结构作为临时起点，重新绑定本Goal；它不是通用无干扰证明，也不能继承仅授权旧exactID的receipt。
- 队列观察在AppLauncher前执行；完整窗口、拒绝原因和等待都落盘。保持GPU/driver身份、显存余量、进程白名单、运行时内存/磁盘/STOP保护，不因低利用率豁免。
- 准入窗口判断发车前的外部负载；不能在本作业训练时拿它自身GPU高利用率触发“空闲≤5%”退场。运行期采用已登记的显存/健康/所有权/超时守卫，外部干扰另行归因；任何新运行期策略先冻结。
- 临时忙碌允许本地有界退避，不为每个观察窗口创建新的live作业或模型调用。队列观察与实际启动时准入分别标注，不能拿先前观测冒充本作业receipt。实际发车时用新鲜完整窗口，逐窗口记录，不删除尖峰/挑子窗口。
- 若完整证据显示规则误判背景波动，可在本次授权内提交一次有依据的调度修订并独审，通过后新身份使用；不能无限改阈值直到放行。初始V2和修订各自完整保留。持续外部负载或6小时排队封顶则停止新作业并交付资源状态。
- 工程故障：先保全、准确清理/结算，再本地诊断；已有确定修复可直接做，需判断时才一次模型介入。修复后以新attempt启动、消耗新资源；不设“第三次失败必问用户”，也禁止未修复的原参数盲重试。
- `app.close` 超时不覆盖原生FAILED退出。只有计数/raw/哈希/所有权清理均完整且独立接受，才可将科学结果单列为可用；未知退出、数据不完整不能套用历史豁免。
- 尽量在退出前原子持久化计数/manifest/最终科学数据；设置独立清理watchdog，只清理本作业所有后代并wait，不能遗漏脱离进程组的telemetry。
- schema/seed不兼容要在CPU预检发现。若新测试需要新评分schema，事前登记并与旧结果分开，不能在评分时改seed标签取得“原套件通过”。
- 资源等待、工程失败、科学阴性、完整成功分别记账/报告；不能互相替代。
