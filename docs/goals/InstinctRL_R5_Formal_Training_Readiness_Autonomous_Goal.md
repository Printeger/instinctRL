## 0. 本次用户委托与执行边界

### 0.1 一次性委托

用户本次明确要求：在 Goal 开始时一次性覆盖完整有界执行范围；离线分析、代码修改、测试、报告、配对实验、独立审核、阶段预算扩展和研究方法转向均由 Codex 自主衔接；不逐阶段询问，只有异常 STOP 才暂停。

启动 prompt 是将该委托交给本地 Codex 的载体。启动后由**现有 Coordinator / Commander 角色**登记新的主任务授权、资源总包络和授权代理范围；Builder 负责实现，Reviewer 负责独立验收。单项 proposal、输入哈希和 release 仍保留，但由受托角色在总范围内自行处理，**不再每项向用户申请一次**。

本文件不声称当前对话已经向本地 rlflow 写入许可或启动任何进程。不得伪造签名、批准 ID、机器权限或 Reviewer 结果。若系统确有不可代理的身份认证/平台权限，只集中报告一次真正的外部阻塞，不能以“需要审批”代替本可完成的代理操作。

### 0.2 授权内容

允许自行完成：

- 读取仓库、已授权的本地原始实验材料及必要主源文献；进行 CPU 分析、真实输入前向/梯度诊断、局部测试。
- 在当前项目内实现 reward、anchor 表征、历史编码、优化、动作参数化、训练时域和课程等**与剩余悬停误差直接相关**的候选。改变方向须在新实验开始前登记理由和可比基线，不必等用户选择。
- 在总资源上限内扩展阶段预算、增加实验/评估入口、调整单次资源上限、执行必要的补测和有原因的重试。每个新入口使用新的身份和真实账本。
- 执行真实仿真短训、纯悬停时域扩展、独立训练种子复验、有限的非零命令衔接测试；冻结正式训练方案与准确入口。
- 局部修复 runner、证据持久化、CPU 分析器、关闭清理及授权衔接，前提是确实影响当前科学任务。隔离安装必要依赖时记录版本，不修改冻结环境；不建设新的通用 orchestration 系统。
- 正常提交、tag 与 push；不 force-push，不改写历史，不删除旧证据。

以下不是可自主改变的“方法因素”：原 Z 指标和阈值、失败分母、原始初始状态/启动窗口、安全与 STOP 门槛、部署信息边界、历史事实、无关用户进程和真实硬件。不得通过硬编码零输出、直接替换 actor 为 B0、添加部署不可得的真值输入，让策略看起来通过。

### 0.3 正式训练的边界

本 Goal 包含**为收敛基础技能而做的训练**，但不在未达标时直接启动原 256-update 混合任务长训。正常结束时，正式方案、资源计划、精确运行身份、授权前提和启动命令必须就绪；**本 Goal 默认不提交正式完整训练作业**。

用户这次委托同时允许 Coordinator 在通过最终独立审核后，登记正式训练的条件式启动许可。实际正式训练作为下一次明确启动动作，不再要求重做一轮科研决策或逐个签发用户许可；执行时仍检查真实 STOP、输入、资源和进程状态。

## 2. 正常结束需要什么证据？

### 2.1 不能把“相对更好”当成总 Goal 完成

单个实验的 `VALID_EXPERIMENT_POSITIVE/NEGATIVE` 都是中间结果。总 Goal 只有下列两种出口：

```text
READY_FOR_FORMAL_R5_TRAINING
STOP_<确切异常原因>
```

方法失败、一次 Z 未达标、评审要求局部修复、阶段额度不够，都不是默认请求用户“是否继续”的理由。完成局部处理后继续下一科学动作。

### 2.2 正式训练准入的硬条件

| ID | 必须完成的验收 |
|---|---|
| G1 方法完整 | 最终 actor、reward、动作、观测、controller、训练阶段和部署信息依赖明确；不存在绕过 actor 的悬停捷径 |
| G2 原 Z 达标 | 最终候选在预先冻结的主节点，通过完整原 Z；32 lane、所有方向子组、所有启动/失败及全部原阈值保持 |
| G3 不是单节点偶然 | 开发 seed 在两个预先登记的后段检查点均通过原 Z；不能在大量已看过节点中事后挑两个最好点 |
| G4 独立种子确认 | 方法/预算/节点冻结后，再使用至少两个未参与该候选调参的训练 seed；两个 seed 的预定主节点均通过原 Z。总计至少三个训练实例达标 |
| G5 学习实现可信 | 新冷启动实验的真实首次 rollout gate 在任一 optimizer 前通过；新增算法/网络版本有对应计算测试和方法身份 |
| G6 非零衔接可执行 | 必要的有限命令切换/训练衔接检查完成，无新 shape、history、参考生命周期或数据索引缺陷；没有把尚未训练的 T/S/X/W 成功当成既成事实 |
| G7 运行可接管 | 真实 checkpoint 可读取并复算身份；同设备/同实现的重算与已登记精度一致；启动、证据保存、退出清理及新账本闭合到允许范围 |
| G8 正式包已完成 | 精确正式源码/config/seed/预算/课程/评价节点/初始或恢复方式/argv/停止规则及代理授权绑定完成，无关键 TODO |
| G9 独立审核 | Reviewer 认可 G1–G8；无阻塞性 MUST_FIX；旧失败和新负结果完整保留 |

G3/G4 是**本任务书新增的准入可靠性要求**，不是此前已完成条件，也不是统计充分性或真机可靠性保证。未经训练的非零任务不要求在本 Goal 预先达到完整策略性能，否则会把“训练准入”和“训练成功”混成同一件事。

若复验失败，就回到研究循环，不能改成“2/3 也算通过”。新候选定稿后使用新的确认 seed，并保留以前的失败 seed 用作回归，不隐藏候选选择过程。

## 3. 自主闭环：一个 Goal 内的五个阶段

```text
接管当前 C1 和真实证据
  → 定位剩余几厘米漂移的时间结构与可用反馈
  → 选择一个可区分解释的候选并冻结对照
  → CPU 测试 + 真实短训 + 原 Z 评价
  → 达标？
       否：分析结果 → 自主调整方法/预算 → 下一轮
       是：冻结方法 → 独立种子复验 → 非零衔接检查
  → 全部准入通过 → 正式训练包 + 独立审核 → READY
```

每轮简短记录：观察、假设、选择理由、唯一主要变化、共同基线、预算、结果及下一动作。允许不同科学问题顺序迭代，不要求整个 Goal 永远只有一个参数变化；**每次因果对照应能解释改变了什么**。

### Phase A：有终点的剩余误差分析

首先复用 C1 全量 Z 轨迹和已保存训练信息，回答四个问题：

1. **漂移何时发生？** 分开原始启动、持续漂移、后段停稳但未恢复；按 lane/reset 连续段分析，保持原评分全窗口不变。
2. **是小速度偏置还是参考恢复问题？** world-frame 位置与同坐标速度积分校核；body velocity 与 sensor/world 位移不能当作严格等式。缺失姿态时声明限制，不编造精确分解。
3. **anchor 是否真的有效？** 统计 active、usable fraction、参考捕获/清除、Huber loss 及奖励尺度；检查有效光束对 XY 平移与姿态改变的敏感性、几何退化和参考重捕获。相关性不自动等于方向性反馈。
4. **策略能否利用参考信息？** 区分 reward 可见、critic 可见、actor 可见和底层反馈可见。当前 anchor 内部参考不自动等于 actor 输入。禁止把增大一个几乎无信息的奖励项当成默认答案。

已有信息足够决定下一试验时就结束 Phase A。缺少必要字段时，先新增小型观测日志；有原因的非训练补测在预算内自行执行，不重新开展全仓库审计。

### Phase B：首选 anchor 单因素，允许证据驱动转向

初始参考基线为当前 C1：actor LR=1e-4、critic LR=3e-4、零命令残差权重=0.05、原 anchor 权重=4。

首选问题：**在 anchor 确实携带 XY 参考误差信息时，提高或重新标定其有效约束，是否能消除剩余位置漂移？** 这沿用仓库下一研究方向，但其有效性还未知。[S2]

先做尺度与信息核查，再登记一个候选系数。4→8 可以作为有尺度依据时的首个候选，不是预设最优值或已证明修复。不能先看训练结果再改本次“预注册”的系数；后续换系数属于新的适应性实验，应新增记录。

若该方向不合适，Coordinator 可自主选择下表中的相关路线，不需返回让用户投票：

| 证据形态 | 允许的下一主变量 | 实验注意事项 |
|---|---|---|
| anchor 有效但有效奖励很弱 | anchor 系数 / 归一化中的一项 | 参数与公式变更分开；不同时修改零命令残差权重 |
| anchor 对 XY 不敏感、频繁无效或主要反映姿态 | 可部署的测量空间参考特征、anchor 表征/有效性机制 | 新增 actor 反馈必须完全来自允许传感器/历史；记录新增维度与计算成本 |
| 原奖励反馈足够，仍出现稳定动作偏置或探索噪声妨碍收敛 | 残差分布、初始化、熵或一个优化设置 | 不能把均值、众数、采样策略切换当作单纯日志修正 |
| 仍明显改善，64 updates 的数据不足以判定 | 纯零命令训练时域扩展 | 参考组与候选同预算；不得偷偷进入原 mixed 阶段 |
| 必要纠偏被零残差代价抑制 | 状态条件化或有容差的残差约束 | 无命令不等于任何时刻都应禁止动作；必须保留抗扰与回正能力 |
| 发现实际观测/history/参考更新实现错误 | 最小实现修复并重建共同基线 | 不把 bug 修复全部归因于新 reward |

方法转向允许改变 reward、表征、历史、优化和课程，必要时也可更换学习方法，但必须先有针对性理由。不要为了“自主”每轮随意换一个完全不同架构。

### Phase C：真实训练、有效比较和适应性扩展

第一轮建议为两组各64 updates、32 env、16-step rollout、原 u16/u64 Z 评估，共65,536 training和25,600 evaluation transitions；只有新方法需要时才改变这些方法设置，并在两组共同基线上处理。

默认 cold start；两组初始化规则、训练 seed、环境条件、总预算、预处理与指标一致。若只改 reward，第一次采样应具有可核对的同源性，returns/advantages 因奖励改变而不同是预期行为。若改 actor 结构，不能要求不同 shape 的权重逐位相同；需要匹配共有组件初始化规则并明确可比性范围。

**不得只拿旧 C1 做完美同期对照的替代品。** 旧数据可筛查；涉及新源码、入口或新训练条件的最终方法结论，需要同版本参考组。已有完全兼容、身份完整的参考结果可复用，并明确其是否同期。

允许根据证据扩展纯悬停训练到128、必要时256 logical updates；这是**本次新委托允许的研究范围扩展**，不是改写旧 Goal 的“不扩256”结论，也不是启动原256-update混合任务正式训练。新训练任务必须显式保持零命令/既定场景，不能仅把 max_updates 改大却自动触发旧 mixed schedule。

扩展预算应在看下一段结果之前登记；同等预算报告不能变成“候选多训一倍、对照不动”。不证明必然收敛；连续有效试验表明平台化时，优先改变有证据支持的机制，不盲目追加时长。

### Phase D：冻结、复验与有限衔接

候选在开发数据通过原 Z 后，冻结：源码、方法、预算、主检查点、评价规则、学习率 schedule、命令分布、停止条件。再选择两个未用于调参的训练 seed 做确认。确认失败不能用追加训练临时补考后仍宣称原冻结方案通过；补救是新的方案与记录。

建议在追加 seed 上保留参考组，以支持改进机制的复验；若为资源效率只复验最终候选，明确只能证实候选达标，不得声称相对效应已跨 seed 复现。

进行有限的零→非零→零、正反方向切换检查。它用于验证新表征、参考点生命周期和训练入口，不要求未训练的策略提前完成整套 T/S/X/W。可从已冻结 checkpoint 的独立副本进行例如8–16 updates 的衔接性训练；必须单独命名、计入训练量，不污染 G2–G4 的确认结果。

若衔接揭示“零命令机制使策略硬性不能响应非零命令”，这是方法有效性缺陷，不能直接 READY。若只是尚未学会跟踪，应由正式阶段课程解决，并在正式计划中保留 Z 防退化检查。

### Phase E：正式训练启动包与最终审核

完成第10节的交付。Reviewer 按 G1–G9 验证真实结果，不以开发者自己的 PASS 代替审核。最终可以在下一次运行命令后直接开始正式训练，不再留下“还需确定方法/预算/入口”的关键问题。

## 4. 实验记录、主要指标与防止“调到通过”

### 4.1 每轮开始前冻结一个小型实验卡

```text
experiment_id / parent_experiment / question
reference_commit / candidate_commit / effective_config_hash
training_seed / evaluation_seed / initialization_or_resume_contract
sole_primary_change / other_required_common_changes
total_training_transitions / evaluation_nodes / primary_node
hypothesis_support_pattern / hypothesis_refutation_pattern
stop_and_resource_limits / delegated_approval_receipt
```

不用新建多层制度；复用现有 JSON/Markdown/账本，能自动生成的表不要手工重复填写。

### 4.2 所有结果同时展示三个层次

1. 更新与分布：首次概率一致性、解析/采样 KL 的准确口径、Beta 参数和方差、梯度/advantage/return。
2. 控制：实际 v_corr、最终目标速度、实际速度及已知的坐标/时序；训练采样和确定性评价分开。
3. 行为：原 Z 成功数、各 lane 完整指标、最大偏差、漂移的时间结构、reset/失败原因。

reward 变大、KL 变小、平均值改善都不能替代原 Z。每次模型选择记录完整候选列表、训练预算和选择规则，不遗漏不利结果。

### 4.3 原指标与部署边界不可迁就候选

不把0.30改成0.35，不剔除启动，不缩短20秒，不改变sensor-T0，不移除最差lane，不将reset后的段拼接为一次成功，不靠“无碰撞”替代所有指标。

禁止将世界位置/真实速度/GT 参考直接传给原受限 actor。新增测量空间参考或历史编码可以是合法方法改变，但必须说明它是从哪些实际可用信号获得、能否部署；critic/reward 的训练真值与actor/底层控制的部署反馈分别登记。

不能把本次全部性能改进说成某一参数的独立贡献。若做小型组合实验，记录因素组合，并至少保留能区分关键贡献的对照；不强制每项工程修复都再做昂贵消融。

## 5. 一次性总授权、分级自动扩展与资源上限

以下数值是**本任务书新设计的建议总授权包络**，不是历史预算，也不是预计耗时。用户采用本任务书与启动 prompt 后，Coordinator 将其写入真实控制面。它给出充足的自动调整空间，但不是无上限占用机器或购买算力。

### 5.1 新 Goal 的总体上限

| 资源 | 初始可分配额度 | 总 Goal 预授权硬上限 |
|---|---:|---:|
| training transitions | 65,536 | **2,097,152** |
| nontraining / evaluation transitions | 25,600 | **1,048,576** |
| live process starts | 4 | **64** |
| simulator initialization reservations | 4 | **64** |
| logical policy updates | 128 | **4,096**，同时受transition上限约束 |
| 实际 actor / critic optimizer steps | 按实验参数推导 | 每类各 **65,536**；新增网络优化也须登记 |
| 训练/恢复 checkpoint writes | 14 | **256** |
| 累计分配 GPU 秒 | 10,840 | **86,400 GPU-seconds** |
| 累计实验进程 wall 秒（含清理） | 10,840 | **86,400 seconds** |
| 新增原件、快照、临时峰值、归档与保守预留 | 首轮按实际绑定，默认≤64 GiB | **min(512 GiB，启动时可用空间减30 GiB)** |
| 并行 GPU 作业 | 1 | **1**，默认串行，不争抢其他用户作业 |
| 外部付费云资源/充值/新增硬件 | 0 | **0** |

GPU-seconds 按分配设备与真实作业结算，不等同于 CUDA kernel 活跃时间。CPU 离线分析仍应有单项资源限制、进展检查和缓存，不因为不计 GPU 而无限运行。多个维度取最先触达的上限。

总上限同时约束失败、重试、复验、恢复、衔接性训练和为后续正式启动登记的资源预留；实际消耗与未消费预留分开计数，避免双扣。不是承诺一定使用这些资源，更不是承诺在这些预算内一定达标。

### 5.2 自动扩展规则

- 初始额度只是第一轮可分配预算，不是每次用完就要找用户的硬终点。
- Coordinator 根据已有结果，写入 `BUDGET_ADJUSTMENT`：扩展原因、原额度/新额度、下一次实验的信息收益、剩余额度与复验预留，然后自行签发新单项许可。
- 方法改变写入 `METHOD_DECISION`，列支持/反证、预期影响及与原方案的区别；实质变更经独立预审后在总预算内自动 release。
- 至少保留总training预算的25%用于最终确认/衔接；另为正式启动留出一份条件式资源预留。默认正式首段若是两组各256 updates及原五节点评价，需预留262,144 training、329,600 evaluation transitions和4个启动槽。这些预留不是本Goal已经执行的量，但参与总额度分配，不能全部花在前期搜索。正式方案缩减或改变时可以记录后重算；不得等Goal结束才发现正式启动还缺另一轮用户预算批准。
- 到达总硬上限仍未满足准入，属于 `STOP_RESOURCE_EXHAUSTED`。不得自动修改总硬上限为无限；交付最佳真实结果和唯一重要缺口，不把失败写成完成。

### 5.3 单项 wall、输出和启动预算允许在总范围内重分配

默认复用已经验证的单项运行限制；确需增加单次 wall 或输出配额，可在启动前记录后自主批准，不必逐次找用户。不能运行超限之后倒填更大的额度，让一次违规变成合规。

任何入口启动前要有明确磁盘余量与上限。大张量无损分块，保存必需证据而非机械复制全量历史；原始证据与归档占用分开记账。新实验可根据已测写入量制定较小但有余量的per-entry配额，无须永久照搬每次16 GiB；**不得借此释放或改写旧账本的保守预留**。

如果原权限系统不能表达主委托下的分配，允许作最小适配：主授权哈希→受托Coordinator→新实验准确spec/AUTH。保留Builder/Reviewer分离，不取消原输入校验、coexistence 或清理机制。

## 6. 不必打断用户的事件与异常 STOP

### 6.1 自主处理并继续

| 事件 | 处理 |
|---|---|
| 分析完成、CPU测试通过、文档/提案生成 | 自动进入下一阶段，不请求“继续” |
| 一次科学负结果、Z仍未达标、某候选更差 | 保留结果，修正假设，选择下一实验 |
| Reviewer 的可修 MUST_FIX | 局部修复、复验、再审核；不把每条意见交给用户 |
| 阶段预算不足、需要新增seed或补测入口 | 在总包络内自动调整、准确记账 |
| 缺失尚未签发的新单项许可 | Coordinator 依据主委托生成真实许可，不伪造旧用户逐项批准 |
| 正常的代码/配置变化 | 新提交、新哈希、新方法身份；不是让运行中的旧输入漂移 |
| 资源短暂占用、coexistence预检拒绝且未创建仿真 | 保留失败及计账；确认无活动作业后按计划有界等待/新入口，不杀无关进程、不放宽阈值 |
| 已知native-close超时，但数据完整且owned清理确认 | 保留FAILED，独立接受可用科学证据并继续下一工作；不重复跑已有完整数据 |

重试必须有原因和新身份。相同未诊断错误不原样连跑；同一环境占用最多3次递增退避预检/恢复尝试，仍不具备运行条件时记为持续资源阻塞。此数值是本任务的新恢复规则，不追溯改变旧Goal的零重试契约。

### 6.2 真正需要暂停的异常

- 用户主动取消，或真实外部 STOP 文件/信号出现。不能自动删除或忽略 STOP。
- GPU/驱动/温度/硬件异常、内存/磁盘安全余量不足，或无法确认进程所有权/无残留。
- 存在未知或可能仍在运行的作业，无法确保不会重复训练/争用设备。
- 证据有不可解释的损坏、身份不一致或数据污染，无法通过可追溯的局部修复建立新有效输入。
- 系统拒绝必要权限，且该身份认证或权限授予无法由已获委托的角色完成。
- 总资源硬上限耗尽；或满足证据标准需要超出本任务不可变的安全/部署边界。

首次概率 gate 或非有限值失败必须立即停止**该次参数更新/作业**。若可以从日志明确定位并在授权范围内修复，保留失败后创建新实验继续，不等于每次都要求用户处理。若反复出现而无法定位，升级为异常 STOP。不得放宽原gate容差掩盖失败，也不能在gate失败后先训练几步试试看。

原生关闭失败的容忍仅限已验证的失效模式和完整owned清理；新的退出异常或无法验证数据时，不能机械沿用先前“非阻塞”的结论。

### 6.3 STOP交付

只发送一个集中的 `STOP_REPORT.md`：确切原因、已做的恢复、仍缺的权限/资源/决策、已完成结果、当前不可触碰的进程/证据，以及明确恢复入口。不要每轮重复同一个阻塞描述。

## 7. 训练时域、恢复与公平比较

**64 updates 不是自然规律，也不是只能在64步内学会才有资格研究。** 它是上一轮筛查预算。本任务允许在看到下一段结果前登记更长的纯零命令训练，检验“数据不足”这一解释；不能未经区分便进入旧mixed课程。

固定实验主节点可以是u64、u128或u256中的一个，由具体问题和训练预算在新运行前决定。要求最终所有确认seed使用同一预算与主节点。需要两个后段检查点的稳定性证据时，在实验卡中预定，例如u96/u128，不能事后改节点。

恢复训练时明确区分：

- 完整训练器恢复：actor、critic、优化器、计数、RNG、课程及已实现状态。
- 仿真重建后fresh reset：若没有保存完整物理/history/anchor/actuator状态，必须如此命名，不能宣称轨迹严格连续。
- 新方法从同一checkpoint分叉：属于warm-start干预试验，不与另一个cold-start结果冒充公平对照。

原生关闭失败而checkpoint完整时可以使用被独立认可的文件，不得因退出码直接丢弃真实数据；也不得只凭文件存在就当作可恢复。

## 9. Reviewer与多角色：独立，但不流程膨胀

Coordinator持续管理研究目标与总预算；Builder单写者负责实现；Reviewer对重要候选和最终结果独立验证。不同子问题可以并行只读分析，但不能多个agent同时写main或运行GPU作业。

小的分析、命名、文档和已测试局部修复不要求每次调用一名新Reviewer。以下节点保留独立检查：实质方法/信息边界变更的prelive、候选实际达标证据、最终确认与正式启动包。

不要把每个子任务都设成单独Goal。使用一个简短的 `GOAL_STATE.md` 持久化当前假设、最近有效运行、版本、剩余预算、下一动作和异常；上下文切换后从该文件与证据索引继续，而不是从头审计。
