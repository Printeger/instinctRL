# 单分支开发流程

生效：2026-10-12。来源：用户在本次会话逐项批准整理方案，包括迁移、CPU 验证、
保留历史、提交和正常推送 main。此授权不增加任何实验或训练预算。

1. 进入固定目录，读取项目状态、当前任务授权、git status 和 HEAD。
2. 日常代码、必要工具、测试和状态在同一 main 分支维护；同一目录单写者。
3. 完成一个可理解的变更后提交。提交按实现职责组织，不设固定次数，不重写已有历史。
4. 实验前提交全部执行源码与配置，保存精确 commit、配置/工具/输入哈希及真实 argv。
5. 用 tag 标识实验输入与验收版本；用只读快照或 detached HEAD 固定运行版本。
   默认不创建任务分支。历史绝对路径绑定保留原 bytes，新候选记录新绑定。
6. CPU 检查、代码同步、独立验收和真实行为验证分别记录；通过测试不等于训练成功。
7. 运行开始后输入冻结。失败原始记录保留；离线重分析生成新记录。不得覆盖旧证据。
8. 用户授权内正常推送；不 force push、不改写历史。同步前核对远端继承关系。

项目状态的唯一阅读入口为 `docs/PROJECT_STATUS.md`；机器状态为 `coordination/PROJECT_STATE.json`。
历史 Commander/Executor 状态原文归档，不能当作新执行许可。

Commander 管目标、契约、预算和独立验收；Builder 管任务内实现、必要验证及交付。
咨询/流程维护不自动获得角色。沿用 V3 的 MUST_FIX、NON_BLOCKING、FOLLOW_UP、
CONTRACT_DECISION 分类，实质缺陷按原任务局部修复，额外需求进入后续任务。
产品、actor、方法、runtime 和资源边界不因单分支整理改变。当前没有新 live 或训练授权。
